# 季绑定通过补建落成普通绑定，按弹幕源记住处理过的条目

季绑定（一季 ↔ 一个合集）不在读取弹幕时按集号对应现算，而是由补建给每一集建出普通的绑定，并按弹幕源记住哪些条目已经处理过：处理过的不再补建，用户删掉的绑定不会被补回来，改集号对应也只影响还没处理过的条目。这样读取路径（弹弹 API、跨源去重）和单集绑定完全一样，偏移、失效、重新拉取都按集管理；代价是多存一份"处理过"的记录。

"处理过"只记季绑定自己建出过绑定的条目。对应的集上已有同一个弹幕源的绑定（手动绑的、另一个季绑定建的）时，补建跳过这个条目：不记处理过，也不把那个绑定算作它建出的；那个绑定被删掉后照常补建。于是 `bindings.season_binding_id` 只表示"由它建出"，条目表、集面板的标签、建出的绑定数和删除时"一起删"说的是同一批绑定。

## Considered Options

- 读取时动态展开：季绑定本身就是弹幕的来源，取弹幕时按集号对应现算这一集的弹幕源。不用落绑定，但每集的偏移、失效、删除无处安放，落库的弹幕也要另找地方存。
- 补建时"缺什么补什么"，不记处理过的条目：实现更简单，但用户删掉的、对错的绑定会在下一次补建时被建回来。
- 集上已有同一个弹幕源的绑定时记为处理过、不动那个绑定（最初的做法）：条目表把它显示成已建绑定，集面板上却不算季绑定的，两处对不上。
- 接管：把已有的同源绑定的来源改成这个季绑定。来源的含义从"由它建出"变成"归它管"，删除季绑定时"一起删"会删掉用户手动建的绑定，两个季绑定对到同一个弹幕源时还要定归属；跳过只多出一条规则：删掉手动绑定后季绑定会把这一集补上。

## 后记

本文说的季绑定都是合集的季绑定。按季上传留下的文件夹的季绑定不补建，没有处理过的记录和条目表，见 ADR 0008。
