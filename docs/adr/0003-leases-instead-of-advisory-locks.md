# 应用的锁用表里的租约，不用 advisory lock

同步、季绑定的补建这两把锁原来是会话级的 advisory lock，持锁期间一直占着一个专用连接。我们改成 `leases` 表里的租约：拿锁是一条只在过期后才能接管的 upsert，持有者每 10 秒续约，30 秒不续约就过期；迁移锁也换成 goose 自带的表锁（同样是租约）。

理由：
- 不再长期占用连接，`database.max_conns` 不需要为持锁的连接留余量。
- 会话级的锁在 PgBouncer 的 transaction pooling 下不可靠；表里的租约与连接无关。
- 锁的状态在表里，"正在补建"直接 JOIN `leases` 判断，不查 `pg_locks`，也能用 SQL 构造过期的租约来测试。
- 网络分区时，advisory lock 要等 TCP 超时连接断开才释放；租约到时就过期。

## Consequences

- 进程崩溃（没来得及释放）后，锁最多 30 秒才过期，期间界面仍显示"同步正在进行""正在补建"，手动触发得到 409。正常关闭会主动释放。
- 持有者丢了租约（续约发现已被接管，或续约一直失败到本地估计的过期时间）时，这一轮的 ctx 被取消，按被打断处理。互斥的保证到锁为止：每次拿锁得到一个单调递增的 token（fencing token），续约、释放都核对它，但业务写入不核对，并发写入仍靠行锁和唯一约束兜底。
- 过期时间按数据库的 `now()` 判断，不受各实例时钟偏差影响；与追更比较的时间仍用应用的时钟，两者无关。
