# 合集的季绑定可以原地换合集，不在新合集里的绑定一起删除

> 已被 ADR 0010 替代。

创建合集的季绑定时填的东西（贴的链接、选的候选、集号对应、集号规则），创建之后应该都能改。集号对应和集号规则原本就保存着、能改；但链接没有保存，选哪个候选只体现在合集 ref 里。贴错了番，或者想从"这个稿件的分 P"换成"它所在的合集"，只能删掉季绑定再重建。我们决定：

1. 合集的季绑定另存一列 `link`，记下创建或换合集时贴的链接，编辑时预填。链接只用来回显，不放进 ref：ref 是"绑的是哪个合集"的规范写法，查重和唯一约束 `(season_id, adapter, ref)` 都依赖"同一个合集只有一种写法"。比如投稿合集的 ref 里没有当初贴的是哪个稿件，加进去之后，同一个合集从不同稿件贴进来就成了两个 ref。这一列之前建的季绑定没有链接，编辑时用 ref 生成的合集链接代替。代价是这些老的季绑定没法从合集切回当初贴的那个多 P 投稿，因为不知道当初贴的是哪个稿件。
2. 编辑与添加用同一套流程：贴链接（预填记下的）→ 预览 → 选候选（默认选中现在的合集）→ 改集号对应、集号规则 → 保存。可以换成任意链接，不限于当初那组候选。
3. 换成另一个合集时原地改季绑定的 ref，它建出的绑定按弹幕源分两种处理：
   - 弹幕源在新合集里的：绑定和处理过的记录都保留，照旧算处理过。投稿合集与多 P 投稿的条目都是 `{aid, page}`，多 P 投稿的条目正好是它在投稿合集里那些条目的子集，在这两者之间切换时两边对得上。
   - 弹幕源不在新合集里的：绑定连同弹幕删除，处理过的记录也删除。这样季绑定名下只有新合集的条目，条目表、"建出 N 个绑定"、删除时的"一起删"说的仍是同一批绑定（ADR 0001）。删除不可恢复，所以编辑时的预览先由后端算出会删掉几个绑定，保存前在确认框里写明。
4. 选出的就是现在的合集（同一个合集的另一种链接）时只改记下的链接，什么都不删。即使合集里已经没有某个条目，它建出的绑定也不删：平时检查时条目从合集里消失，本来就不删它建出的绑定。
5. 换合集时，这个季绑定正在补建就返回 409。进行中的补建列的是原来的合集，会把旧条目写回去，或者建出不在新合集里的绑定。换合集要先拿到这个季绑定的补建租约，一直持有到写完。

## Considered Options

- **链接放进 ref**：没有选，原因见第 1 条，唯一约束会拦不住重复绑定。
- **只在原链接的那组候选之间切换**：不用再贴链接，但创建时要存下全部候选，贴错了番照样只能删掉重建。
- **不在新合集里的绑定变回普通绑定**（同删除季绑定时不勾"一起删"）：不丢数据，但绑错了番时留下一批要逐集删的绑定，而换合集多半就是因为绑错了。
- **不在新合集里的绑定仍算这个季绑定建出的**：什么都不动，但这些绑定不在条目表里，和"建出 N 个绑定"、删除时的"一起删"对不上，违反 ADR 0001。
- **换合集时中止进行中的补建**：用户不用等，但补建的每个写入点都要校验"合集没变"；补建一轮通常很快，等它结束再换就够了。

## Consequences

- PATCH `/api/season-bindings/:id` 多了 `link`、`kind`：传了 `link` 就重新识别、列出合集（最长约 25 秒）。编辑时的预览另有接口 `POST /api/season-bindings/:id/preview`，多返回现在的候选、换过去会删掉的绑定数，以及处理过的条目的绑定建在哪一集。
- 卡片上不再放集号对应和集号规则的输入框，都在"编辑"里先预览、再保存。
