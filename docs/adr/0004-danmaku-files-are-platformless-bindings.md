# 弹幕文件不属于任何平台，绑定用 kind 区分链接与文件

用户可以上传弹幕文件建绑定（目前只支持 B 站导出的 XML）。我们决定：
1. 弹幕文件里的弹幕一律不属于任何平台（`danmaku.PlatformNone`），即使文件是从 B 站导出的；原始弹幕 ID 直接取 XML 里的 dmid。
2. 绑定加一列 `kind`（`link` / `file`）区分两种弹幕源。文件绑定的 `adapter`、`ref` 为空，用 CHECK 约束守住；弹幕文件的解析不实现 `source.Adapter`，也不进 `source.Registry`。

## Considered Options

- **B 站导出的 XML 算 B 站平台**：插件显示 B 站前缀，与在线 B 站绑定按 ID 精确去重。没有选：文件的出处只能从内容推测，不是事实；同一份文件可能被改过、拼过，按平台算会让 cid 与在线弹幕撞上，与 B 站现取的弹幕错误地合并。代价是与在线 B 站绑定之间只靠文本去重，插件把它们显示为"弹弹"。
- **`adapter` 存保留值 `file`**：不用改表结构。没有选：`adapter` 的含义是源适配器的 ID，存一个不是适配器的值等于在列的语义上撒谎；`Registry` 要防着有人注册它，`ref` 还得编一个 ID 凑唯一约束。
- **来源信息拆成子表**（`binding_links`、`binding_files`）：每列都非空，最干净。没有选：绑定本来就是同一个实体，只是来源的形态不同；拆开后读绑定都要 JOIN 两张子表，"恰好有一张子表"数据库约束不了。
- **文件实现 `source.Adapter`**：弹幕文件没有链接，不能重新拉取，也没有合集，六个方法里一半只能空着，违背"方法都要实现、业务代码不做类型断言"的约定。

## Consequences

- 唯一约束 `(episode_id, adapter, ref)` 在 NULL 上不生效，只作用于链接绑定；同一集可以有多个文件绑定。
- 只对一种绑定有效的操作（重新拉取、标为失效、定时拉取；追加文件、重新解析）都按 `kind` 过滤。
- 原始文件存进库（`binding_files`），解析规则改了以后由用户在卡片上重新解析。
